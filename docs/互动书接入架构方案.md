# 互动书接入架构方案

> 版本：0.1（讨论稿）
> 日期：2026-06-23

---

## 一、背景

Epic 阅读器目前支持以下书籍类型：

| 类型        | 值   | 说明                  |
| --------- | --- | ------------------- |
| STANDARD  | 1   | 标准图文书（含 Read to Me） |
| AUDIOBOOK | 2   | 有声书                 |
| ARTICLE   | 3   | 文章                  |
| VIDEO     | 4   | 视频书                 |
| QUIZ      | 5   | 测验                  |

现有第三方扩展机制（Reader Extension）基于 STANDARD 类型书籍，以覆盖层形式叠加互动 UI，无法满足新型互动书的需求。

新型互动书形态（如闯关游戏、解谜、交互叙事）的特点：

- **无页概念**：内容由用户操作驱动，不是翻页式
- **完整应用形态**：第三方提供完整的 Vue3 / React 项目
- **独立渲染**：第三方完全接管内容呈现，宿主提供容器

---

## 二、核心决策

### 2.1 新增书籍类型

新增 `INTERACTIVE = 6`，互动书仍然是"书"，复用书籍的完整生命周期：

- 书架、收藏、推荐（后续支持）
- `/read/:bookId` 路由入口
- 书籍元数据（title、cover、author 等）
- 完成奖励、徽章体系

**早期入口**：暂不走书架/搜索，由运营页面提供专属入口，直链 `/read/:bookId`。

### 2.2 路由策略

两种方案对比：

**方案A：复用 `/read/:bookId`（当前选择）**

优点：

- 书籍加载、权限校验、完成奖励等前后置流程天然复用
- 改动集中，风险可控，快速落地

缺点：

- `ReadComponent` 已较重，新增分支需注意隔离
- 现有不需要的 Services 仍会被实例化

**方案B：新路由 `/play/:bookId`**

优点：

- 完全干净，新组件只包含互动书需要的逻辑
- `ReadComponent` 零改动，现有功能零风险
- 长期可维护性更好

缺点：

- 书籍加载、权限校验逻辑需要单独接入
- 完成奖励、推荐等后置流程需要额外对接，工作量大
- 后端、客户端路由跳转逻辑需同步修改

**结论**：当前阶段选择方案A快速落地，不排除后续迁移到方案B。

**关键约束**：新类型所有逻辑必须高度内聚在独立子组件内，`ReadComponent` 只做最薄的类型判断，不散落任何互动书逻辑。这样将来如需迁移到独立路由，成本接近平移。

### 2.3 扩展接入方式

延续现有 Reader Extension 机制：

- 第三方将项目打包为 **IIFE 格式单 JS 文件**，技术栈不限
- 宿主动态加载，调用 `extension.activate(context)`
- 重型模块（Three.js、page-flip 等）通过 Vite 动态 `import()` 拆成独立 chunk，按需加载
- 宿主只加载入口 JS 文件，后续 chunk 自动从 CDN 拉取

### 2.4 媒体资源

第三方媒体资源（图片、视频、音频等）统一部署到 **Epic CDN**，通过 Context API 传入 `assetBaseUrl`，第三方拼接完整 URL。

```
https://cdn.getepic.com/extensions/{partner}/v{version}/
├── main.js
├── chunk-xxx.js
└── assets/
    ├── bg.jpg
    └── audio.mp3
```

### 2.5 用户登录态

互动书使用 **Epic 登录态**，不依赖第三方认证体系。第三方无需感知用户身份，进度上报通过 `context.progress.save()` 调用，宿主内部负责处理认证，第三方对此完全透明。

## 三、Context API 设计（互动书版本）

互动书的 Context API 与现有 Reader Extension API 独立，针对新类型设计最小集：

```typescript
interface InteractiveBookContext {
  // API 版本
  version: string;

  // 配置信息
  config: {
    assetBaseUrl: string;      // CDN 基础路径，第三方拼接资源 URL 用
  };

  // 书籍数据
  data: {
    getBookId(): number;
    getBookData(): object;     // 书籍元信息
    getLabsData(): string;     // 关卡/内容数据（第三方自定义格式）
  };

  // 进度与完成（接口细节待定）
  // 认证由宿主内部处理，第三方无需关心用户身份
  progress: {
    save(data: object): Promise<void>;   // 上报进度
    load(): Promise<object | null>;      // 读取历史进度
    complete(data?: object): void;       // 通知宿主完成
  };

  // 埋点（透传到 Epic 数据通道）
  analytics: {
    log(event: string, params?: object): void;
  };
}
```

> 注：`progress` 的数据格式（结构、存储方式）待后续与后端对齐后确定。

## 四、数据结构

### 4.1 书籍数据

复用现有 `Book` 类，新增字段极少：

| 字段                             | 类型     | 说明                               |
| ------------------------------ | ------ | -------------------------------- |
| `type`                         | number | 新增 `INTERACTIVE = 6`             |
| `extensionUrl`                 | string | 扩展 JS 的 CDN 地址（已有字段）             |
| `labData`                      | string | 关卡/内容数据 JSON（已有字段）               |
| `extensionConfig.assetBaseUrl` | string | 资源 CDN 基础路径（扩展现有字段）              |
| `extensionConfig.globalName`   | string | 扩展在 window 上注册的全局变量名，取代从文件名解析的方式 |

### 4.2 内容数据（labData）

互动书的关卡数据存在 `labData` 字段，格式由第三方自定义，宿主只透传不解析。通过现有 Open API 写入：

```bash
POST /openapi/book.php?action=upsertLabData
{
  "book_id": 12345,
  "labdata": "{...第三方自定义的关卡 JSON...}"
}
```

## 五、第三方接入要求

### 5.1 打包要求

| 项目   | 要求                             |
| ---- | ------------------------------ |
| 格式   | IIFE，技术栈不限（Vue、React、原生 JS 均可） |
| 文件名  | 统一命名为 `main.js`                |
| 入口   | 独立的扩展入口，不含编辑器、调试、登录模块          |
| 重型依赖 | 使用动态 `import()` 按需加载，减小主 JS 体积 |
| 资源路径 | 使用相对路径，编译时由我们注入 CDN base       |
| CSS  | 打包进 JS，支持 ShadowDOM 注入         |

### 5.2 需要改造的部分

以 Penguin POC 项目为例，主要改造点：

| 改造项                                     | 工作量 | 说明                   |
| --------------------------------------- | --- | -------------------- |
| 新建扩展入口，实现 `activate(context)`           | 小   | 不含 router/auth       |
| Vite 构建配置改为 IIFE                        | 小   | 参考开发文档示例             |
| 媒体路径改用 `context.config.assetBaseUrl` 拼接 | 中   | 替换 `resolveMediaUrl` |
| 移除 `authStore` 依赖                       | 小   | 打包时排除，宿主内部处理认证       |
| 进度上报改用 `context.progress`               | 中   | 替换原有后端接口             |
| 重型模块改为动态 `import()`                     | 小   | Three.js 等           |

预计第三方改造工作量：**2~3 天**（在 Context API 文档完备的前提下）。
